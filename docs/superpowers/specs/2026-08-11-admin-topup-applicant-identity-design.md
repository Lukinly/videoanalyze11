# 管理员充值申请用户身份展示设计

日期：2026-08-11

## 目标

让管理员审核充值申请时能够明确识别申请人，避免只看到积分数量和备注却无法判断应该给哪个账号充值。

## 根因

`credit_topup_requests` 已保存 `user_id`，管理员充值申请 API 也会返回该字段，但当前 `AdminPage` 没有渲染它。用户 ID 本身不便识别，而管理员接口没有返回申请人的邮箱。

## 方案

由管理员 repository 的 `listTopups` 查询关联 `users` 表，在充值申请记录中增加 `userEmail`。管理员 API 原样返回扩展后的记录，前端类型和管理员页面同时接收该字段。

不新增数据库字段，不修改迁移文件，也不依赖管理员用户列表在前端进行匹配。这样即使用户列表分页或筛选，充值申请仍然携带自己的申请人身份。

## 数据契约

管理员充值申请记录包含：

- `id`
- `userId`
- `userEmail`
- `requestedAmount`
- `note`
- `status`
- `reviewNote`
- `createdAt`
- `reviewedAt`

普通用户读取自己的充值申请时继续使用现有数据契约；`userEmail` 只要求出现在管理员列表接口中。

## 管理员页面

每条充值申请显示：

- 用户邮箱，作为主要身份标识。
- 用户 ID，作为辅助核对信息。
- 申请时间。
- 申请积分。
- 用户备注。
- 通过和拒绝按钮。

如果关联用户不存在或邮箱不可用，页面显示“未知用户”，同时保留用户 ID，确保申请仍可追踪。数据库正常情况下用户记录应该存在。

## 错误处理

- 查询邮箱失败时不应把申请错误归属给其他用户。
- 管理员列表加载错误继续使用现有统一错误提示。
- 审核和积分发放仍以充值申请中的 `userId` 为准，邮箱只用于展示，不参与授权或记账。

## 测试

- Repository 测试验证 `listTopups` 返回创建申请用户的邮箱。
- 管理员路由测试验证列表响应保留 `userId` 和 `userEmail`。
- Web 测试验证充值申请同时显示邮箱、用户 ID、申请时间、积分和备注。
- 最终运行相关测试、类型检查、Web lint 和 Web 构建。

## 非目标

- 不修改充值审批、积分发放和审计语义。
- 不新增用户详情弹窗。
- 不新增数据库迁移。
